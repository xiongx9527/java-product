# ai-model-configuration Specification

## Purpose
定义 AI 模型配置的对外契约：字段与校验、模型类型能力、默认模型归属，以及「可用」与「启用」两类状态的生命周期。

## Requirements

### Requirement: 模型配置字段

系统 SHALL 在「配置模型」步骤提供以下字段，并按此顺序展示：模型名称、Base URL、API Key、模型类型、基础模型、是否生效、高级配置。

模型名称 MUST 必填且长度不超过 100 字符，并在同一实例内保持唯一；名称与基础模型完全独立，选择或更换基础模型 MUST NOT 自动改写名称。

Base URL MUST 必填，允许携带多级路径与查询参数，仅拒绝空值和非 `http`/`https` 协议。

API Key MUST 对无障碍标识的标准提供商必填，对标记为私有的提供商可留空。

高级配置 SHALL 收敛为单一折叠区，包含上游格式、完整 URL 开关与模型参数列表；模型参数非空时 SHALL 默认展开，参数区标题 SHALL 显示当前参数数量。

#### Scenario: 新增模型时名称与模型解耦
- **WHEN** 用户将基础模型从 `deepseek-chat` 改为 `deepseek-reasoner`
- **THEN** 模型名称保持用户已填写的内容不变

#### Scenario: Base URL 携带路径
- **WHEN** 用户填写 `https://dashscope.aliyuncs.com/compatible-mode/v1`
- **THEN** 校验通过，且该值按原样保存

#### Scenario: 标准提供商缺少 API Key
- **WHEN** 选定非私有提供商并留空 API Key 提交
- **THEN** 表单校验失败并提示 API Key 必填

#### Scenario: 模型参数自动展开
- **WHEN** 编辑一个已配置 3 条模型参数的模型
- **THEN** 高级配置默认展开，参数区标题显示「模型参数（3）」

### Requirement: 模型类型能力

系统 SHALL 支持 LLM(0) 与 向量(1) 两类模型。

模型类型在编辑态 MUST 只读；新建时 SHALL 默认为 LLM。

模型类型下拉 SHALL 依据当前上游格式的能力矩阵置灰不支持的选项：Anthropic Messages 与 Responses 仅支持 LLM，Azure OpenAI 不支持 Rerank，Chat Completions 支持全部类型。

#### Scenario: 编辑态不可改类型
- **WHEN** 用户打开一个已有模型的编辑表单
- **THEN** 模型类型控件为只读

#### Scenario: 选择 Anthropic 上游格式
- **WHEN** 用户将上游格式切换为 Anthropic Messages
- **THEN** 向量类型选项置灰，且当前类型不为 LLM 时回退为 LLM

### Requirement: 默认模型按类型唯一

每个模型类型 MUST 至多存在一个默认模型；设置某个模型为默认时，系统 SHALL 仅清除同类型的默认标记，不影响其他类型。

默认模型 MUST 同时满足 `valid=1` 与 `enable=1`，否则 MUST 拒绝设默认。

默认模型 MUST NOT 被停用，也 MUST NOT 被删除；用户若要调整，MUST 先将同类型另一个可用模型设为默认。

新建模型 MUST NOT 自动成为默认。

当某类型尚无默认模型时，模型路由 SHALL 回退到该类型下第一个 `valid=1` 且 `enable=1` 的模型，以保证首次配置后即可使用。

#### Scenario: 跨类型互不影响
- **WHEN** 用户将某向量模型设为向量默认
- **THEN** 当前 LLM 默认模型保持不变

#### Scenario: 默认模型不可停用
- **WHEN** 用户尝试关闭当前默认模型的「是否生效」开关
- **THEN** 系统拒绝操作并提示先切换默认模型

#### Scenario: 无默认时回退
- **WHEN** 某类型没有任何默认模型，但存在一个已启用且校验通过的模型
- **THEN** 该类型请求使用该模型

### Requirement: 可用与启用状态

模型 MUST 维护两个独立状态：`valid` 表示最近一次连通校验是否通过，`enable` 表示是否启用。

`valid` MUST 只由连通校验结果回写，保存配置时 MUST 沿用已有值，不得因保存动作改写。

`enable` 仅当 `valid=1` 时可被用户开启；`valid=0` 时开关 MUST 置灰并提示需先通过校验。

校验失败时，系统 SHALL 允许保存为不可用模型，不得阻断保存。

#### Scenario: 未校验模型不可启用
- **WHEN** 一个 `valid=0` 的模型在表单中展示
- **THEN** 「是否生效」开关置灰，用户无法开启

#### Scenario: 保存不改变校验状态
- **WHEN** 用户仅修改模型名称并保存一个 `valid=1` 的模型
- **THEN** 保存后该模型仍为 `valid=1`

#### Scenario: 校验失败仍可保存
- **WHEN** 连通校验返回 401，用户点击保存
- **THEN** 配置被保存，模型状态为不可用且未启用

### Requirement: 会话候选模型范围

工作空间授权列表与 MCP 模型列表 MUST 只返回 LLM 类型且 `enable=1` 的模型；向量模型 MUST NOT 出现在对话可选列表中。

#### Scenario: 向量模型不进入对话候选
- **WHEN** 系统同时存在 LLM 与向量模型，用户打开工作空间模型授权
- **THEN** 列表仅显示 LLM 模型

### Requirement: 向量默认切换后的索引重建

当用户将某个向量模型设为默认，且与当前默认向量模型不同，系统 SHALL 在切换前弹出确认，说明维度可能变化、已有向量将失效、影响术语/训练/表/数据源四类召回。

切换完成后，系统 SHALL 在模型页常驻展示「向量索引待重建」提示，直到重建成功；该状态 MUST 持久化，刷新页面、重新登录或重启服务后仍然可见。

系统 SHALL 提供「一键重新向量」入口。重建 MUST 对四类向量做**全量重算**，MUST NOT 只补 `embedding IS NULL` 的存量行。

重建范围 MUST 覆盖**全部工作空间**，MUST NOT 只处理当前登录用户所在空间：默认向量模型是全局配置，切换后所有空间的术语、SQL 示例、表与数据源向量均失效。

重建 SHALL 复用既有单 worker 守卫，同一时刻只允许一个重建任务；重复点击 MUST 返回「任务进行中」而不是并发启动。

重建 SHALL 按工作空间分批执行并汇总，进度 MUST 同时给出台阶（当前空间）与总量（已完成/总数）。

重建过程 SHALL 展示进度与当前阶段，完成后 SHALL 报告各空间、各类的成功数、失败数与耗时；失败项 SHALL 可重试，且 MUST NOT 因单个空间失败而中断其余空间。

维度变化时，系统 SHALL 重建向量集合，MUST NOT 在旧维度集合上追加新维度向量。

#### Scenario: 切换前确认
- **WHEN** 用户把默认向量模型从 `bge-m3` 切换为另一个模型
- **THEN** 弹出确认框说明需重新向量化且影响所有工作空间，用户确认后才执行切换

#### Scenario: 常驻待重建提示
- **WHEN** 用户切换默认向量模型后关闭页面并重新打开
- **THEN** 模型页仍显示「向量索引待重建」提示

#### Scenario: 一键重建覆盖全部空间
- **WHEN** 系统存在 3 个工作空间，用户点击「一键重新向量」
- **THEN** 三个空间的四类向量全部重算，进度与结果按空间汇总展示

#### Scenario: 全量重算而非补空
- **WHEN** 已有向量的记录在重建时被处理
- **THEN** 这些记录的向量被重新计算并覆盖，而不是跳过

#### Scenario: 单空间失败不影响整体
- **WHEN** 第 2 个工作空间重建时抛错
- **THEN** 其余空间继续执行，结果中单独列出该空间的失败原因与可重试入口

#### Scenario: 重复触发被拒
- **WHEN** 重建任务进行中用户再次点击
- **THEN** 返回「任务进行中」，不会启动第二个任务

#### Scenario: 维度变化
- **WHEN** 新模型维度与旧索引维度不同
- **THEN** 向量集合按新维度重建，旧维度向量不再参与检索

### Requirement: 向量维度与存储对齐

向量模型 MUST 具备向量维度属性，并持久化在 `ai_model.dimension`。

维度 SHALL 由连通校验自动探测（取 embeddings 响应中 `data[0].embedding` 的长度）；用户 MAY 在高级配置中手动覆盖，覆盖值 MUST 为正整数。

维度取值 SHALL 生效于三处：模型列表展示、向量重建、向量存储集合创建与校验，三者 MUST 使用同一来源。

向量存储 MUST 与该维度对齐：重建时按模型维度创建/校验集合；维度不匹配的存量向量 MUST 视为无效并在重建中被覆盖，MUST NOT 与不同维度向量混存。

查询时 MUST 跳过维度不匹配的向量并记录数量，MUST NOT 因长度不一致抛出异常或返回错误分数。

维度校验 MUST 覆盖三处，任一处不一致即视为「未对齐」：

| 校验点 | 规则 |
| --- | --- |
| 启用（`enable`） | 模型 `dimension` 必须已探测（非空）且 `valid=1`，否则拒绝开启 |
| 设为默认 | `state.model_id` 必须等于该模型 id 且 `state.dimension` 等于该模型 `dimension`，否则拒绝并提示先重建 |
| 问答入口 | 每次请求前校验当前默认向量模型与 `state` 一致，不一致则阻断并提示重建 |

运行期 MUST 校验上游实际返回的向量长度：与模型 `dimension` 不一致时 MUST 判定本次调用失败，MUST NOT 写入存储。

写入存储时 MUST 校验 `vector.length == dimension`，不一致 MUST 拒绝写入并记日志。

切换默认向量模型时，提示 MUST 展示「旧维度 → 新维度」，维度不同时提示文案 MUST 明确指出需要重建索引。

#### Scenario: 校验自动探测维度
- **WHEN** 用户对向量模型执行连通校验，上游返回 1024 维向量
- **THEN** 模型维度被记录为 1024，并在表单中展示

#### Scenario: 手动覆盖维度
- **WHEN** 用户在高级配置中把维度改为 1536
- **THEN** 保存后模型维度为 1536，重建按该维度执行

#### Scenario: 维度不匹配的存量向量
- **WHEN** 索引中存在 768 维旧向量，当前模型为 1024 维
- **THEN** 查询跳过这批旧向量，重建后全部覆盖为 1024 维

#### Scenario: 未探测维度不可启用
- **WHEN** 向量模型从未执行过连通校验，`dimension` 为空
- **THEN** 「是否生效」开关不可开启

#### Scenario: 未对齐不可设默认
- **WHEN** 模型的 `dimension` 与 `state.dimension` 不一致
- **THEN** 设为默认被拒绝，并提示先执行重建

#### Scenario: 未对齐阻断问答
- **WHEN** 切换默认向量模型后尚未重建，用户发起问数
- **THEN** 请求被阻断并提示「向量索引待重建」

#### Scenario: 返回维度不符
- **WHEN** 上游返回的向量长度与模型 `dimension` 不一致
- **THEN** 本次调用判定失败，向量不写入存储

#### Scenario: 切换时提示维度变化
- **WHEN** 用户从 768 维模型切到 1024 维模型
- **THEN** 确认框展示「768 → 1024」并说明需重建索引

### Requirement: 向量模型必须为在线模型

向量能力 MUST 只使用配置在 `ai_model` 中的在线向量模型（`model_type=1`）。

系统 MUST NOT 回落到本地 ONNX 模型；本地向量模型相关代码、依赖与配置 MUST 一并移除，避免出现「看起来可用、实际走本地」的隐性路径。

向量模型可用性判定 MUST 与 LLM 一致：`enable=1` 且 `valid=1`。

当不存在可用在线向量模型时，系统 SHALL 阻断所有问答入口（网页会话、MCP 对话、定时任务），返回统一的可读错误，MUST NOT 静默使用本地模型或词法召回冒充向量召回。

模型配置页 SHALL 在无可用在线向量模型时展示明确提醒，并引导到向量模型配置。

#### Scenario: 未配置在线向量模型
- **WHEN** 系统没有任何可用的在线向量模型，用户发起问数
- **THEN** 请求被阻断并返回「未配置可用的在线向量模型」，不产生回答

#### Scenario: 在线向量模型被停用
- **WHEN** 唯一的在线向量模型被停用
- **THEN** 问答同样被阻断，错误信息与未配置一致

#### Scenario: 不再回落本地
- **WHEN** 在线向量模型调用失败
- **THEN** 请求失败并报错，MUST NOT 回落到本地 ONNX 模型

#### Scenario: 依赖与配置清理
- **WHEN** 改造完成后检查构建产物与配置
- **THEN** 不存在 ONNX 运行时依赖、本地模型目录配置与相关文档说明

### Requirement: 参考实现功能对等

本系统 MUST 以 SQLBot（`/Users/xiongxiao/Workspace/Idea/codes/SQLBot`）作为 AI 模型模块的参考实现，保持功能对等。

除 `reference-parity.md` 第 4 节列明的 7 项有意偏离（D1–D7）外，SQLBot 已有的接口、表单交互、参数缓存与运行时行为 MUST 全部保留，MUST NOT 以实现成本为由删减。

新增能力 MUST 以叠加方式实现，MUST NOT 替换或削弱既有行为；改造后的 Chat Completions 路径行为 MUST 与改造前一致。

#### Scenario: 基础模型联动地址
- **WHEN** 用户选中带自带地址的基础模型
- **THEN** Base URL 自动填充为该模型地址，模型名称保持不变

#### Scenario: 参数按提供商与模型缓存
- **WHEN** 用户配置了 `供应商 A + 模型 X` 的参数，切到模型 Y 后再切回模型 X
- **THEN** 之前的参数被恢复

#### Scenario: 默认模型删除保护
- **WHEN** 用户尝试删除默认模型
- **THEN** 返回与 SQLBot 一致语义的错误提示，删除被拒绝

#### Scenario: 首建不再自动设默认
- **WHEN** 用户创建系统内第一个模型
- **THEN** 该模型不自动成为默认（有意偏离，见 `reference-parity.md` D1）

### Requirement: 模型路由统一入口

所有相邻模块 MUST 通过 `ChatModelRouter` 的对话模型与向量模型入口获取模型，MUST NOT 直接读取模型仓储或自行拼装类型与状态过滤条件。

模型候选口径 MUST 统一为「模型类型匹配 + `enable=1` + `valid=1`」；MCP 模型列表、工作空间授权、嵌入式问答、定时任务与权限判定 MUST 复用同一口径。

调用方 MUST 处理「无可用模型」的情况，返回可读错误提示，MUST NOT 抛出空指针或静默失败。

#### Scenario: MCP 模型列表过滤
- **WHEN** 系统存在一个已停用的 LLM 模型和一个向量模型，用户调用 `mcp_model_list`
- **THEN** 返回列表不含该停用模型与向量模型

#### Scenario: 定时任务无可用模型
- **WHEN** 所有 LLM 模型均未通过校验，定时任务触发
- **THEN** 任务记录失败原因「无可用对话模型」，而不是空指针异常

#### Scenario: 向量模型不可用时阻断
- **WHEN** 唯一的向量模型被停用
- **THEN** 问答入口返回「未配置可用的在线向量模型」，不再降级为词法召回

「自定义」提供商（`id=15`）MUST 使用专用图标表示「可接入任意兼容端点」，不得复用 OpenAI 品牌图标。

提供商名称、类型标签等界面文案 MUST 通过 i18n key 取值，不得硬编码。

新增自定义提供商标识时，MUST 同步补齐 `en`、`zh-CN`、`zh-TW`、`ko-KR`、`th-TH` 五份语言文件，缺失任一语言即视为未完成。

#### Scenario: 自定义提供商图标
- **WHEN** 用户在「选择提供商」步骤查看列表
- **THEN** 「自定义」显示独立的插头图标，与 OpenAI 图标可区分

#### Scenario: 五语言文案齐备
- **WHEN** 将界面语言依次切换为五种语言
- **THEN** 「自定义」提供商名称均有对应译文，不出现 key 原文或空白
